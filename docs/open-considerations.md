# 要検討事項（AI駆動開発の仕組み）

参考: 書籍『プロフェッショナルAI駆動開発』の紹介スライド。
必要性は感じるが、個人開発（週8〜10時間）では今すぐ実現しにくいものを置いておく。
このファイルは CLAUDE.md から参照しない（Claudeのコンテキストに入れないため）。自分用のメモ。

着手の目安は「その問題が実際に起きたら」とする（先回りしない）。

## 1. 別のAIによる相互レビュー

- 内容: スライドは「別のAIによる独立したレビュー」を勧めている。現状の `design-reviewer` は、同じモデルを別コンテキストで動かしているだけで、盲点が共通する
- 難しい点: 別ベンダーや別モデルのAPI契約、キー管理、費用、呼び出し手順の整備
- 着手の目安: 独立レビューを通したのに、自分が見て明らかな問題が複数回見つかったとき

## 2. GitHub Actionsによる全PRの自動AIレビュー

- 内容: ローカルの `/pr` を使い忘れても、すべてのPRにAIレビューがかかる状態にする（スライドの3層レビュー「テスト → AIレビュー（全PR）→ 人間」の第2層を、仕組みで保証する）
- 難しい点: APIキーのSecrets管理、従量課金、ワークフローの設定と保守。公式のGitHub Actions連携が使えるかは、導入時に最新の情報で確認する
- 着手の目安: `/pr` を使わずにPRを出す日が出てきたとき

## 3. 並列実行とモデルの使い分け

- 内容: 同じタスクを複数のAIに並列で試させて良いものを選ぶ。工程ごとにモデルを使い分ける
- 難しい点: git worktreeの運用、トークン費用、結果を比較して選ぶ自分の時間。週8〜10時間では、比較のコストが得より大きくなりやすい
- 着手の目安: 同じIssueで手戻りが何度も出るとき

## 4. 機械判定の範囲外にある領域

- 内容: 機械判定を成立させにくい箇所が3つある
  - LLMが生成する週次まとめの品質（出力が確率的で、正解を決められない）
  - フロントエンド（現計画ではテスト対象外。lintと型チェックのみ）
  - Terraform（`plan` までで、実際の挙動は確認できない）
- 難しい点: LLM出力の評価基準づくり（形式・長さ・禁止事項などの契約テストにとどめるか、人が見るか）
- 着手の目安: 週次まとめの品質で手戻りが出たとき。まずは形式の契約テストだけ置く

## 5. 手本となるコードの整備

- 内容: スライドは「シニアのコードをAIが参考にする」を勧めている。個人開発では、自分が納得した実装を「手本」としてAIに参照させる
- 難しい点: 現状は手本にできるコードがまだない
- 着手の目安: Walking skeletonが完成したら、層ごと（router / service / repository / バッチhandler）に手本のファイルを1つ決めて、CLAUDE.md に書く

## 6. 計画レビューの負担

- 内容: 非自明な変更ごとに、計画の作成とAIレビューと承認を挟む運用が、週8〜10時間の中で重くならないか
- 判断方法: 数週間回して、計画を書く時間が実装時間の2割を超えるなら、非自明の基準を絞る

## 7. 自分の理解が追いつくか

- 内容: スライドの流れでは、人間は「手動テスト・レビュー」だけを担う。しかし、設計判断を自分の言葉で語れるようになることが目的なので、AIレビューを通すだけでは足りない
- 対策案: 週に1回、その週の設計判断を1つ選び、自分の言葉で書く（Zenn記事のネタにもなる）
- 着手の目安: PRの「設計判断」を、AIの文章のままコピペして出している週が続いたとき

## 適用しないもの

- フィーチャーフラグ、カナリアリリース: 本番ユーザーが数人の段階では不要。ユーザーが増えたら検討する
- ハーネス環境の共有資産化、組織展開のガバナンス: チーム開発向け
