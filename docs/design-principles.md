# 設計原則（moodLog）

設計・実装・リファクタの前に読む。原則は「守る規則」ではなく「トレードオフを判断する道具」。
適用した原則、あえて適用しなかった原則は、PRの「設計判断」に1行で書く。

## 判断の順序

1. まず単純に動くものを書く（KISS / YAGNI）
2. 変更の痛みが実際に出たら、その痛みに対応する原則を適用する
3. テストが書きにくい → 依存性逆転（DI）・関心の分離を疑う
4. 1つの変更で複数箇所を直している → DRY・凝集を疑う
5. 迷ったら単純なほうを選ぶ

## 原則の要点

| 原則 | やること | やりすぎ（禁止） |
| --- | --- | --- |
| DRY | 同じ「知識・ルール」を1箇所に置く | 見た目が似ているだけのコードの共通化。フラグ引数で分岐する共通関数。共通化は3回目に同じものが出てから（3回ルール） |
| KISS | 読む人が最短で理解できる書き方 | reduce/map/filterの入れ子などの凝った書き方 |
| YAGNI | 今必要な機能だけ作る | 使う予定のない設定項目・拡張ポイント・プラグイン機構 |
| 関心の分離 / 高凝集・疎結合 | HTTP入出力・業務ルール・DBアクセスを分ける | 小さな処理まで層を増やす |
| 単一責任 | 変更理由が1つになるよう分ける | 1メソッド1クラスに細分化 |
| 依存性逆転（DI） | DB・LLM・時刻・外部APIは外から渡す | 実装が1つしかなく差し替える予定もないものに、抽象を作る |
| 開放閉鎖 / インターフェース分離 / リスコフ置換 | 種類が2〜3個に増えた時点で適用 | 1種類しかない段階での先回り |
| 継承より合成 | 部品を持たせて組み合わせる | 実装の再利用のためだけの継承 |
| 契約による設計 | 入力検証（pydantic・型）、前提・保証を明示 | assertの乱用 |
| 最小驚き | 名前と挙動を一致させる（getで更新しない、引数を破壊しない） | - |

## スタック別の適用

技術スタックと役割で、使う原則を変える。

### Backend（FastAPI / Python）
- 層は `router`（HTTP入出力のみ）→ `service`（業務ルール）→ `repository`（DBアクセス）。依存は上から下の一方向
- DB・LLM API・現在時刻は、FastAPIの `Depends` かコンストラクタ引数で注入する（DI）。テストではfakeに差し替える
- リクエスト/レスポンスはpydanticモデルで契約を表現する
- 重視する原則: 関心の分離、単一責任、DI、契約による設計
- 後回し: 開放閉鎖・インターフェース分離・リスコフ（種類が増えてから）
- クラスは「呼び出しをまたいで保持する状態がある」ときだけ。それ以外は関数

### 非同期バッチ（EventBridge → SQS → Lambda）
- handlerは薄く保つ。入力を受けて `service` を呼ぶだけで、業務ルールをhandlerに書かない
- 処理は冪等にする（同じメッセージが2回届いても結果が同じ）。これを契約として明記する
- LLM呼び出しは小さなインターフェース（Protocol）の裏に置き、テストではfakeを使う

### Frontend（Next.js / TypeScript）
- 表示（components）とデータ取得（hooks / APIクライアント）を分ける
- 関数コンポーネント＋hooksを使う。クラス、継承、SOLIDの型階層は持ち込まない
- propsと API レスポンスに型を付けて契約とする
- 共通化は3回ルール。似たコンポーネントを早まって1つにしない
- 見た目（色・文字・余白・角丸・コンポーネント）とアクセシビリティは、DADSに従う。ルールの正は `.claude/rules/dads.md`

### Terraform
- DRYよりも読みやすさを優先する。モジュール化は、同じ構成が3回出るか2環境目が必要になってから
- 環境差分は変数で表す。IAMは最小権限

## アーキテクチャの方針（現段階）

- 採用: レイヤード（router / service / repository）＋DI
- 不採用: クリーンアーキテクチャ、ヘキサゴナル、DDD。業務ルールが複雑化し、層の分離が痛みとして出たときにADRで判断する（YAGNI）

## 実装前・PR前の自己チェック

- 抽象化は、今ある実装・呼び出しの数で正当化できるか（使うのが1箇所なら作らない）
- 新しい外部依存（DB・API・時刻）を、直接呼ばずに注入しているか
- 設計判断（採用案・不採用案・理由）を、自分の言葉で説明できるか
