# 0010 画面のトークンは sessionStorage に持ち、oidc-client-ts で扱う

## 状況

ログインはCognitoのマネージドログインで行い、画面は認可コードフロー＋PKCEでトークンを受け取る（ADR 0009）。ADR 0009 で、受け取ったトークンをブラウザのどこに持つか（XSSへの耐性に関わる）を、構築するときに決めることにしていた（Issue #59）。

あわせて、PKCE、`state` の確認、認可コードとトークンの交換、トークンの更新を、自分で書くかライブラリを使うかを決める必要があった。

## 決定

- トークン（IDトークン、アクセストークン、リフレッシュトークン）は sessionStorage に持つ
  - 再読み込みしてもログインが続き、タブを閉じれば消える
  - XSSが起きればスクリプトから読めるのは localStorage と同じ。XSSへの耐性はトークンの置き場所では上げず、XSSを起こさない側（Reactのエスケープに任せ、`dangerouslySetInnerHTML` を使わないなど）で守る。CSP などの対策は、ユーザーの入力を表示する機能（日次の記録）を作るときに見直す
- PKCE とトークンの扱いには oidc-client-ts（`3.5.0`）を使う。トークンの置き場所が sessionStorage なのは、このライブラリの既定
  - 依存は jwt-decode の1つだけで小さい
  - OpenID Connect の仕様どおりに、ディスカバリー文書から窓口を読む。Cognito に固有の部分はログアウトだけ（Cognito のディスカバリー文書には `end_session_endpoint` がないため、Cognito の `/logout` へ自分で移る。`frontend/lib/auth.ts`）
- APIにはアクセストークンを `Authorization: Bearer` で送る。検証は API Gateway の JWT オーソライザーが行う（ADR 0009）

## 捨てた選択肢

- メモリだけに持つ: XSSには最も強い（ページのスクリプトの変数にしかない）が、再読み込みのたびにCognitoへリダイレクトし直すことになる。リフレッシュトークンも持てない
- localStorage に持つ: タブを閉じても残るため、共用PCでログアウトし忘れたときの影響が大きい。XSSへの耐性は sessionStorage と同じ
- クッキー（HttpOnly）に持つ: スクリプトから読めないのでXSSに強いが、トークンをクッキーに入れて返すサーバー側の仕組み（BFF）が要る。静的エクスポートで配信していて、そのためのサーバーがない
- PKCE などを自分で書く: `state` の確認やトークンの更新を自分で書くと、セキュリティの不具合を作りやすい
- AWS Amplify を使う: 認証以外の機能も含んで大きい。マネージドログインを使うなら、Amplify の UI 部品も要らない
