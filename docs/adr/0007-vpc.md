# 0007 VPCをTerraformで作る

## 状況

RDS（Issue #9）は、AWSアカウントに最初からあるデフォルトVPCに置く前提で構築した（ADR 0002の結果欄）。しかし東京リージョンにデフォルトVPCがなく、`terraform plan` が `no matching EC2 VPC found` で失敗した（Issue #36）。デフォルトVPCが消えた経緯は分かっていない。

VPCを用意する方法として、デフォルトVPCを作り直すか、TerraformでVPCを作るかを検討した。

## 決定

TerraformでVPCを作る（`infra/network.tf`）。構成は最小にする。

- VPC: `10.0.0.0/16`
- プライベートサブネット: `10.0.1.0/24`（ap-northeast-1a）、`10.0.2.0/24`（ap-northeast-1c）。RDSのサブネットグループに2つ以上のAZが必要なため
- インターネットゲートウェイ、NATゲートウェイ、パブリックサブネットは作らない

## 捨てた選択肢

- デフォルトVPCを `aws ec2 create-default-vpc` で作り直す: コマンド1つで済むが、Terraformの管理外の前提が増える。今回の障害も、その前提が崩れて起きた。また、デフォルトVPCのサブネットはすべてパブリックサブネットで、DBを置く場所として必要以上に開いている
- 外部モジュール（`terraform-aws-modules/vpc` など）を使う: 新しい依存が増える。設計原則では、モジュール化は同じ構成が3回出てから
- パブリックサブネットやNATゲートウェイも今作る: 今は使わない。NATゲートウェイは月約45ドルかかる

## 結果

`infra/network.tf` で作成し、`infra/db.tf` のサブネットグループとセキュリティグループをこのVPCに付け替えた（Issue #36）。追加費用はない。

NATゲートウェイもVPCエンドポイントもないため、VPC内に置いたLambdaからは、インターネットにもSSM Parameter StoreなどのAWSサービスにも届かない。Lambdaを置くとき（Issue #10）に、接続情報の渡し方と外向きの経路（VPCエンドポイント、NATゲートウェイ、デプロイ時に環境変数で渡す、など）を決める必要がある。

その後、Issue #10 で、Lambdaには接続情報をデプロイ時に環境変数で渡すことにした（Terraformが `/moodlog/database_url` の値をLambdaの環境変数 `DATABASE_URL` に入れる）。Lambdaは実行中にSSMを読まないので、VPCエンドポイントもNATゲートウェイも作らず、追加費用はない。VPCエンドポイント（月約20ドル）は費用の面で採らなかった。値はLambdaのコンソールでも見えるが、tfstateには元から入っている。
