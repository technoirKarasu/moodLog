# 0009 ログインはCognitoで、Googleとメールアドレスの両方に対応する

## 状況

READMEのコア機能に「Oauthログイン」がある。ログインの方式によって、ユーザーテーブルの設計と、AWSに足すサービスが変わるため、テーブル設計の前に決める（Issue #33）。

ログイン画面は、よくある「Googleでログイン」と「メールアドレスでログイン」が並ぶ形を想定している。

制約: API用のLambdaはVPCのプライベートサブネットにあり、インターネットへ出る経路がない（ADR 0007）。そのため、Lambdaの中からGoogleなど外部のサーバーを呼ぶ方式は、NATゲートウェイ（月約45ドル）を足さない限り使えない。

## 決定

- 認証には Amazon Cognito のユーザープールを使う
- ログインの方法は2つ
  - Google（Cognitoの外部IDプロバイダとしてつなぐ）
  - メールアドレスとパスワード（Cognitoのユーザープールで管理する。パスワードの保存、確認コードの送信、パスワードの再設定はCognitoが行う）
- ログイン画面は、Cognitoのマネージドログインを使う。画面からは認可コードフロー＋PKCEでトークンを受け取る。マネージドログインはEssentialsプラン以上の機能なので、プランはEssentials（新しいユーザープールの既定）にする
- APIのトークン検証は、API Gateway（HTTP API）のJWTオーソライザーで行う。Lambdaに届く前に検証が済むので、Lambdaは外へ出る必要がない
- **同じメールアドレスでも、Googleでのログインとメールアドレスでのログインは別のユーザーとして扱う**。2つを1人に結び付ける処理（Pre sign-up トリガーのLambdaでアカウントをリンクする）は作らない。分けて使いたい人もいると考えたため。結び付けたいという要望が出たら見直す
- DBのユーザーテーブルに持つのは、アプリ内のID、Cognitoの `sub`（ユーザーごとに一意。一意制約を付ける）、作成日時だけ。メールアドレスなどの個人情報はDBに持たない。メールアドレスが要るのは今のところ画面の表示だけで、画面がIDトークンのクレームから読む。バックエンドはCognitoのAPIを呼ばない（VPC内のLambdaからCognitoのAPIを呼ぶにはVPCエンドポイントかNATゲートウェイが要る。週報のメール送信など、バックエンドでメールアドレスを使う機能を作るときに、費用を含めて見直す）
- 確認コードのメールは、まずCognito標準の送信機能で送る（AWSアカウント全体で1日50通まで。上限は引き上げられない）。足りなくなったら Amazon SES に切り替える

料金の見込み: Essentialsプランでは、Googleでログインするユーザーも、メールアドレスで登録したユーザーも、同じ枠で数える。月1万人まで無料で、超えた分は1人あたり月0.015ドル（2026-10時点の Amazon Cognito の料金ページ）。初期の利用者数では、追加費用はない。

構築するときに合わせて直すこと:

- API GatewayのCORSで、`Authorization` ヘッダーを許可する。本番のAPIに残している `http://localhost:3000` の許可を見直す（`infra/api_gateway.tf`）
- マネージドログインからの戻り先（コールバックURL）に、CloudFrontの公開URLとローカル開発用のURLを登録する
- Googleの `email` をCognitoの `email` 属性にマッピングする。しないと、Googleでログインしたユーザーの IDトークンに `email` が入らない
- 画面が受け取ったトークンをブラウザのどこに持つか（メモリか localStorage か）を決める。XSSへの耐性に関わる

## 捨てた選択肢

- FastAPIでOAuthを自前で実装する（authlib など）: LambdaからGoogleのトークン発行の窓口を呼ぶため、NATゲートウェイが要るか、LambdaをVPCの外に出してRDSに届かなくなる。パスワードの保存や再設定も自分で作ることになる
- GoogleのIDトークンを、CognitoなしでAPI Gatewayが直接検証する: 構成は少ないが、リフレッシュトークンがなく1時間ごとに取り直しが要る。メールアドレスでのログインにも対応できない
- Auth0・Clerk などの外部の認証サービス: BaaS/PaaSを使わず、AWSの運用を自分で持つ方針（ADR 0001）に合わない
- 最初はGoogleだけにし、メールアドレスでのログインを後から足す: 足すときの手戻りは小さいが、想定しているログイン画面を最初から作る
- Apple・GitHubでのログイン: Appleは Apple Developer Program（年99ドル）が要る。GitHubは対象ユーザー（社会人）に合わない。必要になったら足す
- 最初からSESでメールを送る: 送信元アドレスの確認と、サンドボックス（決まった宛先にしか送れない状態）の解除申請が要る。初期の利用者数なら標準の送信機能で足りる

## 結果

`infra/auth.tf` と `infra/api_gateway.tf` で構築した（Issue #59）。Google とメールアドレスの両方でログインし、トークン付きで API を呼べることを確かめた。

- 上の「構築するときに合わせて直すこと」は、すべて Issue #59 で行った
  - CORS の `http://localhost:3000` の許可は残した。トークンはクッキーではなく `Authorization` ヘッダーで送るので、許可するオリジンが増えてもトークンは漏れないため（`infra/api_gateway.tf` のコメント）
  - トークンの置き場所は ADR 0010 で決めた
- JWT オーソライザーは `$default` ルートに付け、認証なしのルートは `GET /health` とプリフライト（`OPTIONS /{proxy+}`）だけを個別に作った。新しい API を足したときに、認証なしで公開しないため
- 認証なしの OPTIONS のルートには、Lambda の統合を付けた。付けないと `$default` に落ちて 401 になる（Issue #59 で確かめた）。届いたプリフライトには FastAPI が 204 を返し、CORS のヘッダーは API Gateway が付ける
- マネージドログインからの戻り先は、トップページ（`/`）にした。静的エクスポートでは `/callback` が `callback.html` になり、CloudFront から引けないため
- マネージドログインのドメインは、ログイン画面の URL として公開されるため、AWS アカウント ID ではなくランダムな接尾辞で一意にした
- ユーザーテーブル（`users`。`cognito_sub` に一意制約）は、日次の記録（Issue #66）で作った
- ユーザープールを作り直すと全員の `sub` が変わり、これまでの記録が見えなくなる。そのため削除保護を付けた（Issue #86）
