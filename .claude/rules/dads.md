# フロントエンド設計ルール：デジタル庁デザインシステム（DADS）準拠

このプロジェクトのUIは、デジタル庁デザインシステムβ版（DADS）に準拠して設計・実装する。
基準バージョン: v2.18.1（2026-10-14時点）。バージョンが更新されている可能性があるため、迷ったら一次情報を確認する。

## 0. 大原則

- 色・文字サイズ・余白・角丸などの値は、思いつきで決めない。DADSの定義に従い、定義がないものは「スタイルガイドで決める値」としてトークン化（CSS変数 or Tailwind theme）してから使う。
- DADSに書かれていない具体値（色コード、トークン名、コンポーネントの細部）を記憶や推測で書かない。必ず一次情報かパッケージ実体を確認する。
- DADSから外れる場合は、コード内コメントまたはPR説明に「どこをなぜ外したか」を1行残す。
- アクセシビリティ要件（コントラスト比、フォーカス、色だけに頼らない表現）は見た目の好みより優先する。

## 2. 実装方針

- コンポーネントは、公式のReact版コードスニペットを起点にする。同等のものをゼロから自作しない。
- スタイルはTailwind CSS v4 + `@digital-go-jp/tailwind-theme-plugin` を使う（ADR 0008）。
  - CSSに `@import 'tailwindcss';` と `@import '@digital-go-jp/tailwind-theme-plugin/v4';`
  - プラグインのバージョンはFigmaデザインデータのバージョンと対応関係がある。導入時にREADMEの対応表と最新のnpmバージョンを確認する。
- 色・文字・余白はプラグインが提供するトークンを使う。任意値（`text-[#123456]`、`p-[13px]` など）は原則禁止。

## 3. タイポグラフィ

- フォント: 本文は `'Noto Sans JP', sans-serif`、コードは `'Noto Sans Mono', monospace`。
- 本文・UIの文字サイズは **16px以上** が基準。14pxは補助情報（フッター等）や領域制約がある場合のみ。**14px未満は原則使用しない。**
- 本文の `line-height` は **1.5以上**（推奨は1.6〜1.75）。CSSでは単位なし数値で書く（`%`は使わない）。見出しは本文より狭めてよい（1.4〜1.5）。
- テキストスタイルは5種類（トークン名は `種別-サイズ太さ-行高` 形式。例: `Std-17N-170`）。
  - Display（Dsp）: ページ冒頭の大見出し・ヘッドコピー。行高140%
  - Standard（Std）: 見出し・本文の標準。基本16px以上
  - Dense（Dns）: 管理画面・データテーブルなど情報量優先
  - Oneline（Oln）: ボタン等UIの1行テキスト。行高100%
  - Mono: コード表示。行高150%
- 太さは N（400）と B（700）の2段階が基本。
- 日本語テキストに `font-style: italic` は使わない。
- リンクの下線など、デフォルトの `text-decoration` を理由なく消さない。

## 4. カラー

- コントラスト比: **テキスト 4.5:1以上、非テキスト（枠線・アイコン・区切り線）3:1以上。** 白・黒以外の背景色の上では必ず再確認する。
- 色の役割: キーカラー（プライマリー/セカンダリー/ターシャリー/バックグラウンド）、共通カラー（ニュートラル）、機能カラー、アクセントカラー、セマンティックカラー。
- アクセントカラーは多用しない。装飾以外の用途で使う場合もコントラスト比を守る。
- セマンティックカラー: 成功=緑、エラー=赤、警告=黄/オレンジ。**意味と色相を入れ替えない**（エラーを緑にしない）。明度・彩度の調整は可。
- リンク色: 未訪問=青、訪問済み=紫（4.5:1以上）。リンクは色だけで示さず下線も付ける。
- **フォーカスインジケーター（Yellow-300 + Blackの二重構造）は変更禁止。** `outline: none` で消さない。
- 情報を色だけで伝えない（エラーは色 + アイコン + テキスト、など）。

## 5. 余白

- 基準単位は **8px**。スケールは3〜5段階程度に絞り（例: 8 / 24 / 64）、同種の要素には同じ値を使う。
- 近い要素は関連あるものとして見られる。関連が強いものは小さい余白、弱いものは大きい余白で区切る。
- 見出しの階層が上がるほど周囲の余白を大きくし、階層を余白でも表現する。

## 6. 角の形状

- 5段階: なし(0) / スモール(8) / ミディアム(16) / ラージ(32) / フル(円・高さの50%)。
- 横長の要素は同じ印象になるよう半径を小さめに補正する（例: ミディアムは正方形16、長方形12／ラージは正方形32、長方形16）。
- コンポーネント単位で角丸値を決めて統一する。ページ内でバラバラにしない。

## 7. レイアウト

- 12カラムグリッドを基本とする（1〜4カラムのレイアウトは12カラムの分割で作る）。
- ブレークポイントの標準例: **768px未満**（モバイル・タブレット）/ **768px以上**（デスクトップ）。必要なら追加してよいが、まず2段階で設計する。
- ガターは本文文字サイズの2倍を確保する。ページ左右のマージンも必ず確保する。

## 8. アクセシビリティ

- 達成基準は JIS X 8341-3:2016 / WCAG 2.2 を前提とする。
- セマンティックなHTML（見出し階層、`button`/`a` の使い分け、`label` とフォーム部品の関連付け）を使う。`div` にクリックイベントを付けて済ませない。
- キーボード操作のみで全機能が使えること。フォーカス順序が視覚順序と一致すること。
- コンポーネント実装前に、該当コンポーネントのページ（`/dads/components/<name>/`）の「アクセシビリティ」節を読む。

## 9. 作業手順（Claude Codeへの指示）

1. 新しい画面・コンポーネントを作る前に、DADSに該当コンポーネントがあるか確認する（コンポーネント一覧 → React版スニペット）。
2. あればスニペットをベースにする。なければ、基本デザイン（色・文字・余白・角丸）のトークンだけで組み立てる。
3. 実装後、以下を自己チェックして結果を報告する。
   - 文字サイズ16px未満・行高1.5未満がないか（例外は理由つき）
   - 任意値のハードコードがないか
   - コントラスト比（テキスト4.5:1／非テキスト3:1）
   - フォーカス表示が消えていないか、キーボードだけで操作できるか
   - 色だけで意味を伝えていないか
